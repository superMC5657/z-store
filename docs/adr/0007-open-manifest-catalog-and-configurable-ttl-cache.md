# ADR-0007: 开源清单仓库动态同步与客户端按需 API 详情拉取（含可配置 TTL 缓存）

- **状态**: Accepted
- **日期**: 2026-09-05
- **决策者**: 架构团队与用户共同裁决

## 上下文

在既有实现中，应用清单随安装包静态打包入客户端内存，深度详情在首次拉取后永久存储于本地 SQLite 数据库（终身读库）。这种机制虽然减少了网络请求，但存在严重缺陷：
1. **数据永久脱节**：开源软件一旦发布新 Release、更新 Changelog 或修复安全漏洞，客户端无法感知，详情弹窗中永远显示陈旧版本与旧下载直链；
2. **收录无法动态演进**：新增收录软件、调整分类或别称必须强行发布新的桌面客户端安装包；
3. **API 速率限制矛盾**：在保护 GitHub 未认证 60次/小时速率限制的同时，缺乏灵活的缓存保鲜与按需失效机制。

## 决策

1. **开源清单仓库模式（Manifest Repository）**：
   - 应用收录清单（名称、`owner/repo` 坐标、分类、中文别名、官方图标）由公开开源仓库维护；
   - 客户端内置随包打包的 `catalog.json` 作为**离线种子兜底**；
   - 客户端启动及在设置页中支持通过国内镜像加速节点增量同步远程最新清单，利用 ETag 条件校验实现零成本热更新。

2. **按需 API 动态拉取与 ETag 协商保鲜**：
   - 彻底废除“终身读库”的死缓存机制；
   - 用户在客户端点击应用卡片时，根据清单中的坐标按需请求 GitHub API 获取最新版本与构建资产；
   - 引入 **ETag 协商机制（`If-None-Match`）**：上游未发布新版本时返回 `304 Not Modified`，不消耗 API 配额并延长保鲜期；上游发布新版本时返回 `200 OK` 并更新数据库。

3. **用户可配置的详情缓存保鲜期（TTL）**：
   - 在客户端设置中心开放「应用详情缓存保鲜期 (TTL)」配置项（键名 `detail_cache_ttl_minutes`），提供 `0 分钟（实时校验）`、`10 分钟`、`30 分钟（默认推荐）`、`1 小时`、`6 小时`、`24 小时` 多档可选项，持久化至 SQLite `user_settings` 表；
   - 在 TTL 保鲜期内重复打开详情弹窗直接读取本地缓存（0ms 秒开）；超过 TTL 自动发起条件校验；
   - 详情弹窗提供显式「刷新」按钮，支持即时强制同步最新 Release。

4. **离线与弱网优雅降级**：
   - 当远端网络不可用或触发限额时，客户端自动优雅降级为展示历史缓存，并在详情界面标注“离线缓存”指示，确保不出现白屏或崩溃。
